# 为什么需要 Agent Harness？

## 一句话

很多智能体「演示时流畅无比，生产环境立马原形毕露」，根因往往不是模型不行，而是模型周围的那套基础设施（Harness）不够完善。

## 行业普遍存在的痛点

当前 AI 工程领域有一个非常普遍的怪象：

- **演示环境**：任务上下文干净、路径单一、无并发压力、工具副作用可忽略，智能体表现得行云流水；
- **生产环境**：任务成功率断崖式下跌，错误开始滚雪球，上下文膨胀，工具调用频繁失败，系统无法稳定运行。

绝大多数开发者的第一反应是：**模型不行，要换更强的模型。**

但事实恰恰相反——**问题从来不在模型本身，而在模型周围的那套基础设施。**

## 两个把行业打醒的实验

### 1. LangChain：只改 Harness，不改模型

LangChain 团队在 **TerminalBench 2.0** 评测中做了一个教科书式的实验：

- **没有改动**模型权重和底层算法；
- **只优化**了包裹大语言模型的 Harness 架构；
- 结果：智能体成绩从 **30 名开外直接飙升至第 5 名**。

> 同一个模型，Harness 不同，性能天差地别。这是 Harness 价值最直接的证据。

### 2. LLM 自主优化 Harness

有研究团队更进一步：让 LLM **自主优化 Harness 架构**，任务通过率直接冲到 **76.4%**，吊打所有人工设计的系统。

> 这暗示 Harness 的设计空间远超人工经验所能穷尽的边界——它本身就是一个可以持续被优化的「可进化系统」。

## 为什么「换模型」是治标不治本？

展开思考，演示与生产之间的落差，本质来自四个环境差异：

| 维度 | 演示环境 | 生产环境 |
| --- | --- | --- |
| 上下文 | 短、干净、单线程 | 长、膨胀、多任务交错 |
| 工具调用 | 少、结果可控 | 频繁、结果不确定、有真实副作用 |
| 错误 | 几乎不发生 | 网络抖动、限流、权限、格式异常频发 |
| 状态 | 一次对话结束即丢弃 | 需要跨会话持久、可恢复 |

裸模型只解决「这一个 token 该怎么生成」，而生产环境的绝大部分失败，发生在模型**之外**的环节：

- 上下文过长导致「丢失在中间」（Context Rot）；
- 工具返回的结果无法被模型正确读取；
- 一次瞬时错误导致整条任务链崩盘；
- 没有状态保存，长任务中断后一切归零。

这些都不是「换个更强的模型」能解决的，而是 **Harness 架构问题**。

## 术语的时间线

- 这套理念其实早已渗透在每一个生产级 AI 应用里（编排、工具、记忆等能力早已存在）；
- **2026 年初**，Agent Harness 这个术语被全球 AI 社区正式定义，成为可被讨论、可被设计、可被比较的一等工程概念。

## 结论

> 两个一模一样的模型，只因为 Harness 设计不同，性能可能天差地别。当你的智能体掉链子时，先别急着责怪模型——低头看看它的 Harness，问题大概率就出在这里。

## 思考题

1. 你上一个「演示成功但上线翻车」的智能体，失败发生在模型推理环节，还是发生在上下文、工具、状态、错误处理环节？
2. 如果要给现有智能体做一次 Harness 体检，你会从哪几个模块开始排查？
