# 抉择 6：工具范围

## 问题

给智能体注册多少个工具合适？直觉上「越多越强」，行业数据却给出反直觉的答案。

## 反直觉结论

> **工具越多，性能越差。** Vercel 砍掉 80% 的工具后，性能反而提升。

### 为什么「多」反而「差」？

| 原因 | 解释 |
| --- | --- |
| 选择困难 | 工具越多，模型每次决策的选择空间越大，选错概率越高 |
| 上下文稀释 | 工具 Schema 占据上下文，挤占有效信息空间 |
| 描述干扰 | 大量工具描述互相干扰，模型难以区分「该用哪个」 |
| 幻觉空间 | 工具多时，模型更容易幻觉出不存在的调用或错配参数 |

## 核心原则

> **只暴露当前步骤所需要的最小工具集（Minimal Tool Set）。**

### 两层含义

1. **全局层面**：系统不注册无用工具——每个工具都要回答「什么场景真正需要它」；
2. **动态层面**：即使是已注册的工具，也要**按步骤按需暴露**——当前步骤用不到的工具，不让模型看到。

## 如何实现「最小工具集」？

### 1. 按任务阶段动态注入

```
任务开始（规划阶段）→ 只暴露「检索/规划类」工具
任务执行（编码阶段）→ 暴露「文件/命令/测试类」工具
任务收尾（验证阶段）→ 暴露「测试/检查/提交类」工具
```

- 每个阶段模型看到的工具清单不同；
- 呼应模块 5（提示词组装）：工具定义按需注入，而不是一次全给。

### 2. 工具分组与命名空间

- 把工具按领域分组（如 `file.*`、`web.*`、`data.*`）；
- 需要时整组暴露，减少逐工具管理的开销。

### 3. 定期审计工具清单

- 上线后监控：哪些工具被高频使用、哪些从未被调用；
- 从未调用的工具要么删、要么优化描述——**存在但没人用的工具就是纯负担**。

## 案例：Vercel 的经验

- Vercel 团队砍掉 80% 的工具（从大量工具缩减到核心子集）；
- 结果：性能反而提升；
- 启示：工具不是资产，**用得上的工具才是资产**；注册工具时要有「删除的勇气」。

## 思考与原则

### 1. 工具质量 > 工具数量

- 一个描述清晰、Schema 准确的核心工具，胜过十个含糊工具；
- 工具描述质量直接影响调用正确率（模块 2）。

### 2. 与「子智能体拆分」联动

- 当任务需要的工具确实很多（>10 个重叠）时，不要硬塞给一个智能体；
- 而是拆分子智能体，让每个子智能体只暴露自己的工具子集（呼应抉择 1）。

### 3. 新工具要「先验证再上线」

- 新工具先小范围试用，验证「确实提升任务成功率」再推广；
- 避免「加个工具以防万一」——那万一永远不发生，只是徒增负担。

## 决策速查

| 你的情况 | 建议 |
| --- | --- |
| 工具列表膨胀 | 审计：删掉从未被调用的工具 |
| 模型频繁选错工具 | 精简工具集 + 优化描述 |
| 任务多阶段 | 动态按阶段注入工具 |
| 工具确实很多 | 拆分子智能体，各配子集 |

| 维度 | 要点 |
| --- | --- |
| 反直觉结论 | 工具越多性能越差 |
| 案例 | Vercel 砍 80% 工具，性能反升 |
