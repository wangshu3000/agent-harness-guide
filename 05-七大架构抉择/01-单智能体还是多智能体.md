# 抉择 1：单智能体还是多智能体？

## 问题

搭建智能体系统时，第一个架构抉择就是：用一个全能智能体，还是拆成多个专业智能体协作？

## 行业共识

> **先榨干单智能体的性能。多智能体有额外开销，只有工具重叠超 10 个或任务域明显分离的时候，才考虑拆分。**

## 两种方案的权衡

| 维度 | 单智能体 | 多智能体 |
| --- | --- | --- |
| 上下文 | 单一上下文，信息集中 | 上下文隔离，互不污染 |
| 复杂度 | 低，好维护 | 高，需调度、通信、协调 |
| 成本 | 低（无通信开销） | 高（上下文复制、消息传递、协调开销） |
| 能力边界 | 受单一上下文限制 | 可扩展，承载更大更复杂任务 |
| 失败影响 | 单点失败即整体失败 | 可局部失败、局部重试 |
| 性能风险 | 工具太多/信息太多时下降 | 任务域分离时性能提升 |

## 拆分的两条判断标准

### 标准 1：工具重叠超 10 个

- 当所有智能体都要用同一批 10+ 个工具时，工具清单本身就成了上下文负担；
- 分而治之：每类任务只暴露它需要的子集工具（呼应《工具范围》抉择：工具越少性能越好）。

### 标准 2：任务域明显分离

- 子任务属于**不同专业领域**（如代码 + 文案 + 数据分析）；
- 或需要**不同的工具集、不同的知识背景**；
- 此时合并成一个智能体，上下文互相干扰，得不偿失。

## 为什么不建议「默认多智能体」？

- **额外开销真实存在**：上下文复制、Agent 间消息传递、调度编排、失败传播；
- **复杂度爆炸**：N 个智能体的协作复杂度远高于 N 个单体任务之和；
- **收益未必兑现**：任务域不分离时，多智能体与单智能体性能相当甚至更差；
- 行业教训：很多团队一上来就搭多智能体，结果问题全出在「智能体之间的沟通」上，而不是任务本身。

## 思考与原则

1. **从单开始**：MVP 先用单智能体跑通，性能不够再拆；
2. **按证据拆**：拆分的依据是「工具重叠数」「任务域分离度」等客观指标，不是感觉；
3. **拆后要治理**：子 Agent 也要有护栏、错误处理、验证，不是拆出去就撒手；
4. **拆的粒度要小**：能拆成 2 个就不拆 3 个，通信路径越少越好。

## 决策速查

| 你的情况 | 建议 |
| --- | --- |
| 任务简单、工具少 | 单智能体 |
| 工具重叠 >10 个 | 拆分 |
| 任务域明显分离 | 拆分 |
| 说不清要不要拆 | 先不拆，榨干单智能体再评估 |
