# 抉择 7：Harness 的厚度

## 问题

Harness 应该做多厚？**薄 Harness** 信任模型、少包一层；**厚 Harness** 用编码显式控制逻辑。这是整个 Harness 设计里最根本的哲学抉择。

## 两种路线的对比

| 维度 | 薄 Harness | 厚 Harness |
| --- | --- | --- |
| 哲学 | 信任模型，模型负责智能决策 | 用代码锁死流程，Harness 负责控制 |
| 复杂度 | 低——运行时极简 | 高——大量显式逻辑、状态机、规则 |
| 控制力 | 弱——把控制权交给模型 | 强——每个环节都可编程控制 |
| 迭代速度 | 快——模型变强直接受益 | 慢——逻辑都要人工演进 |
| 风险 | 模型不可控时翻车 | 流程锁死扼杀模型灵活性 |

## 核心规律

> **模型越强，越应该偏向薄 Harness。**

### 为什么？

1. **模型在吸收 Harness 的能力**：后训练阶段会把特定 Harness 范式纳入训练循环，模型「天生就会」越来越多原本需要 Harness 教的技能；
2. **薄 Harness 是放大器**：模型升级时，薄 Harness 不加复杂度也能承接更强能力（面向未来测试）；
3. **厚 Harness 是锁链**：逻辑写死越多，模型升级带来的红利越难释放——Harness 反而成了瓶颈。

## 什么时候必须厚？

厚 Harness 不是贬义词——在特定条件下它是唯一选择：

| 条件 | 为什么必须厚 |
| --- | --- |
| 模型能力不足 | 模型还不可靠，需要 Harness 兜底（流程锁死、严格校验） |
| 任务风险极高 | 医疗、金融、生产变更——流程必须确定性可控 |
| 合规要求 | 每一步都要审计、可复现，不能靠模型自主发挥 |
| 业务规则复杂 | 大量业务约束必须用确定性代码表达 |

## 什么时候应该薄？

| 条件 | 为什么可以薄 |
| --- | --- |
| 模型能力强 | 推理、工具调用、长上下文都可靠 |
| 任务允许自主 | 结果可由验证循环兜底，不需要流程锁死 |
| 迭代速度优先 | 快速试错，不想被 Harness 逻辑拖慢 |
| 模型升级频繁 | 薄 Harness 才能吃到每一代模型的提升红利 |

## 实践中的动态平衡

成熟团队往往**不选边站**，而是动态调整：

```
系统初期（模型弱/需求变）→ 厚一点：多兜底、多校验
系统成熟（模型强/路径稳）→ 逐步减薄：删冗余封装
模型升级后 → 重新评估：哪些 Harness 逻辑已可以被模型内化
```

> 本质：**Harness 的厚度是模型信任度的函数**——信任多少，就包多少。

## 思考与原则

### 1. 减薄要有依据，不是拍脑袋

- 删掉一个模块/封装前，先问：模型现在真的能内化这件事吗？
- 用「面向未来测试」验证：删掉后，模型升级是否能补上？（见演进趋势篇）

### 2. 薄 ≠ 裸奔

- 薄 Harness 仍要有护栏、验证、错误处理——只是更精炼；
- 薄的应该是「流程控制」，不是「安全底线」。

### 3. 厚薄是演进态，不是终态

- Harness 不是一次设计定终身；
- 随着模型升级，定期做「减薄体检」：哪些逻辑已经可以被模型取代？

## 决策速查

| 你的情况 | 建议 |
| --- | --- |
| 模型能力强、任务允许自主 | 薄 Harness |
| 风险高、合规严、流程必须锁死 | 厚 Harness |
| 模型在快速升级 | 倾向薄，做面向未来测试 |
| 不确定 | 从厚起步兜底，成熟后逐步减薄 |

## 小结

| 维度 | 要点 |
| --- | --- |
| 薄 Harness | 信任模型，运行时极简，模型升级直接受益 |
| 厚 Harness | 代码锁流程，确定性可控，兜底能力强 |
| 核心规律 | 模型越强，越应该薄 |
| 动态平衡 | 厚度 = 模型信任度的函数，随演进调整 |
| 关键测试 | 面向未来测试：模型升级后无需加厚也能变强 |
