# 抉择 2：ReAct 循环还是计划-执行循环？

## 问题

编排循环的两种主流形态：**ReAct 循环**（边想边做）与**计划-执行循环**（先计划后执行）。该选哪种？

## 两种循环的对比

| 维度 | ReAct 循环 | 计划-执行循环 |
| --- | --- | --- |
| 模式 | 推理→行动→观察，交替迭代 | 先规划出完整步骤，再逐步执行 |
| 灵活性 | 高——随时根据观察调整 | 低——按计划走，偏离需重规划 |
| 每步成本 | 高——每一步都要完整推理 | 低——执行阶段不再频繁推理 |
| 并行度 | 低——严格串行 | 高——计划内独立步骤可并行 |
| 适用 | 路径不明、探索性强、动态调整的任务 | 路径清晰、可预规划、步骤独立的任务 |

## 两种循环的详细拆解

### ReAct 循环

- **流程**：思考（Reason）→ 行动（Act）→ 观察（Observe）→ 再思考……
- **优点**：灵活，能边做边改——适合「不确定下一步会怎样」的任务；
- **缺点**：每一步都要完整推理 → 每步成本高、延迟高；
- **本质**：以灵活性换效率。

### 计划-执行循环（Plan-and-Execute）

- **流程**：先规划（把任务拆成可执行的步骤清单）→ 再执行（按清单逐步跑，减少中途推理）；
- **优点**：规划与执行分离，执行阶段开销低、可并行；
- **缺点**：计划可能不准确，执行中偏离预期时需要重新规划；
- **本质**：以效率换灵活性。

**LLMCompiler** 的数据给出了量化结论：

> LLMCompiler 的调度数据显示：计划-执行类设计**比顺序 ReAct 快 3.6 倍**。

### 为什么快这么多？

- ReAct 每步都要「读完整上下文 + 完整推理」——串行且昂贵；
- 计划-执行先花一次成本把任务拆成 DAG（有向无环图），然后**独立步骤并行执行**；
- 并行 + 减少重复推理 = 数量级的延迟下降。

## 但快 ≠ 好：什么时候用哪种？

| 你的任务特征 | 推荐 |
| --- | --- |
| 路径未知、需要探索试错 | ReAct（灵活优先） |
| 步骤可预规划、依赖明确 | 计划-执行（效率优先） |
| 延迟敏感、步骤多、可并行 | 计划-执行（LLMCompiler 风格） |
| 需求模糊、频繁变更 | ReAct |
| 混合任务 | 计划-执行框架 + 执行中允许 ReAct 式纠偏（Hybrid） |

## 思考与原则

### 1. 这是「效率与灵活」的权衡

- 没有绝对最优，只有场景适配；
- 要快 → 计划-执行；要稳（不跑偏）→ ReAct；要又快又稳 → Hybrid。

### 2. 计划本身也是成本

- 计划-执行的前提是「能规划出好计划」；
- 任务太模糊时，规划本身就是浪费——先让模型 ReAct 探路，再切计划-执行是常见做法。

### 3. 现代趋势：混合循环

- 成熟 Harness 往往提供两种循环，按任务动态选择；
- 甚至让模型自己决定：探索阶段用 ReAct，成熟阶段用计划-执行。

## 决策速查

| 你的情况 | 建议 |
| --- | --- |
| 追求最低延迟、步骤可并行 | 计划-执行（LLMCompiler 思路） |
| 任务开放、路径不明 | ReAct |
| 流程复杂、既求快又要可控 | 混合：计划-执行 + 纠偏 |

## 小结

| 维度 | 要点 |
| --- | --- |
| ReAct | 边想边做，灵活但每步成本高 |
| 计划-执行 | 先规划后执行，效率高、可并行 |
| 硬数据 | LLMCompiler 比顺序 ReAct 快 3.6 倍 |
| 本质 | 灵活性 vs 效率的权衡 |
