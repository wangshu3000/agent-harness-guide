# 抉择 5：权限与安全

## 问题

护栏要设多严？**宽松模式**高效但有风险，**严格模式**安全但低效——怎么平衡？

## 两种模式的对比

| 维度 | 宽松模式 | 严格模式 |
| --- | --- | --- |
| 效率 | 高——操作放行快，少打断 | 低——每次都要检查、确认 |
| 安全 | 风险高——危险操作可能漏网 | 安全——红线坚决拦住 |
| 用户体验 | 流畅 | 频繁确认，体验笨重 |
| 适用 | 内部工具、低风险环境 | 生产系统、高风险操作 |

## 行业最佳实践：按风险分级，而不是一刀切

成熟的生产系统**不做二选一**，而是**分级授权**：

```
高风险操作（删除、支付、外发、写生产数据）
   → 严格：必须用户确认 + 权限二次校验
中风险操作（写文件、执行命令、调用外部 API）
   → 标准：权限检查 + 沙箱隔离，默认放行可审计
低风险操作（读文件、搜索、查询）
   → 宽松：直接放行，只留审计日志
```

## 核心原则

### 1. 默认最小权限

- 智能体默认只有完成任务所需的最小权限；
- 需要更多权限时「按需临时放开」，用完收回；
- 类比：操作系统用户没有 root 权限，需要时 sudo 提权并留痕。

### 2. 权限执行与模型推理解耦

- 模型负责「想做什么」，权限系统负责「能不能做」；
- 模型永远无法「说服」权限系统放行——权力被架构隔离（Anthropic 设计，见模块 9）；
- 这是防止「模型越权」的根治方案，而不是靠提示词约束。

### 3. 高风险操作必须人在环上

- 删除、支付、外发、生产变更等操作，**必须用户明确确认**；
- 人工确认是最后防线，也是责任边界；
- 确认机制要防「自动点击」：确认请求要展示清晰的操作描述与影响。

### 4. 安全要可审计

- 每次权限检查、每次放行/拦截都要记录；
- 安全事件必须可复盘、可追溯、可问责；
- 「没有日志的放行 = 没有安全」。

## 宽松与严格之外的第三维：信任体系

成熟系统用「信任等级」动态调整模式：

| 信任等级 | 依据 | 模式 |
| --- | --- | --- |
| 可信环境 | 沙箱内、无真实资源 | 宽松 |
| 半可信 | 项目加载时建立的信任（Claude Code 三阶段把关） | 标准 + 检查 |
| 不可信/高风险 | 外部输入、生产资源 | 严格 + 人工确认 |

> 关键洞察：**安全不是静态开关，而是动态的信任评估**——同一系统对不同操作、不同阶段采用不同强度。

## 思考与原则

### 1. 平衡点在哪里？

平衡点由**风险成本**决定：

- 一次危险操作造成的损失 > 日常效率损失 → 调严；
- 确认机制导致用户放弃使用 → 调宽（但高风险操作永不调宽）。

### 2. 别用「提示词约束」代替权限控制

- 提示词里写「不要删除文件」是软约束，模型可能忽略；
- 权限系统是硬约束，架构上就不让执行；
- 安全底线必须用确定性机制，不能依赖模型自觉。

### 3. 失败要显式

- 权限不足时，智能体应「明确告知 + 请求授权」，而不是静默降级或硬闯；
- 「用户可修复错误」的路径要清晰（呼应错误处理模块）。

## 决策速查

| 你的场景 | 建议 |
| --- | --- |
| 内部沙箱、Demo | 宽松模式 |
| 生产系统 | 分级授权：高风险严格 + 中风险标准 + 低风险宽松 |
| 外部数据/不可信输入 | 信任评估 + 严格护栏 |
| 涉及资金/隐私/生产变更 | 全链严格 + 人在环上 |

## 小结

| 维度 | 要点 |
| --- | --- |
| 两种模式 | 宽松（高效有风险）/ 严格（安全低效） |
| 正解 | 按风险分级授权，不做一刀切 |
| 核心原则 | 最小权限、权限与推理解耦、高风险人工确认、全程可审计 |
| 进阶 | 信任等级动态评估，安全是动态平衡不是静态开关 |
