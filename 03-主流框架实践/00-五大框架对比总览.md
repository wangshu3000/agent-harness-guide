# 五大主流框架对比总览

> 全球主流智能体框架是如何落地 Agent Harness 的？它们的设计哲学、技术路径、适用场景有何差异？这对我们选择、搭建自己的智能体至关重要。

## 一表看懂五大框架

| 框架 | 背后团队 | 设计哲学 | 核心抽象 | 状态管理 | 多智能体 | 最强场景 |
| --- | --- | --- | --- | --- | --- | --- |
| **Claude Agent SDK** | Anthropic | 薄 Harness，信任模型 | `query()` 智能体循环 | Git 提交 | Fork / Teammate / Worktree | 深度绑定 Claude，轻量高效 |
| **OpenAI Agents SDK** | OpenAI | 代码优先，开发者友好 | `Runner` 类 | 四种策略可选 | Agents-as-tools / Handoffs | 快速落地生产应用 |
| **LangGraph** | LangChain | 显式图结构，可调试 | 状态图（节点+边） | 类型化字典+归约器+检查点 | 嵌套状态图 | 复杂、多分支长流程 |
| **CrewAI** | CrewAI | 角色分工，团队协作 | 智能体/任务/团队 + Flows | 内置任务执行状态 | 基于角色的多智能体 | 团队式多角色协作 |
| **AutoGen**（微软智能体框架） | 微软 | 对话驱动编排 | 对话即协作协议 | 会话状态 | 五种编排模式 | 开放式多智能体交互 |

## 核心模式高度趋同

先看「同」——五大框架无论设计哲学多么不同，都围绕同一套核心模块构建：

- **编排循环**：都有主循环驱动「推理 → 行动 → 观察」；
- **工具**：都支持工具注册、Schema 定义、结果回传；
- **记忆/上下文**：都处理历史、状态、上下文的维护与持久化；
- **多智能体**：都提供了子 Agent 的机制；
- **验证/护栏**：生产级场景下都提供安全与质量保障手段。

> 这说明「十二大核心模块」不是某家公司的发明，而是**智能体工程的公理集**——框架只是对公理的不同实现。

## 设计哲学截然不同

再看「异」——这是选择框架时真正需要关注的：

| 维度 | 薄派（Anthropic） | 显式派（LangGraph） | 代码派（OpenAI） | 角色派（CrewAI） | 对话派（AutoGen） |
| --- | --- | --- | --- | --- | --- |
| 控制方式 | 信任模型，少包一层 | 图结构显式建模流程 | 原生 Python 代码 | 角色与任务声明式配置 | 对话消息驱动 |
| 复杂度模型 | 极简运行时 | 复杂但精确 | 低学习成本 | 中 | 中 |
| 可调试性 | 依赖模型行为 + Git | 节点级调试、时光倒流 | 标准 Python 调试 | 任务级追踪 | 对话记录追踪 |
| 心智负担 | 低（交给模型） | 高（要画图） | 低（就是代码） | 低（声明式） | 中（要设计对话协议） |

## 没有绝对优劣，只有场景适配

| 你的场景 | 推荐框架 | 理由 |
| --- | --- | --- |
| 已有 Claude 生态，追求极简 | Claude Agent SDK | 薄 Harness、深度耦合、开箱即用 |
| 快速构建生产级应用，团队熟悉 Python | OpenAI Agents SDK | 代码优先、托管工具、上手快 |
| 流程复杂、分支多、需要精确控制与调试 | LangGraph | 显式图结构，一切可追溯 |
| 业务天然按角色/团队分工（如运营+审核+客服） | CrewAI | 角色化声明，贴近组织结构 |
| 开放式、自由协商的多智能体交互 | AutoGen | 对话即协议，编排模式丰富 |
| 多框架对比、大规模复杂系统 | 可组合使用 | 核心模块标准化后，跨框架迁移成本低 |

## 选型思考框架

选框架本质是选「复杂度分配」：

1. **你把复杂度交给谁？**
   - 交给模型（Anthropic：模型足够强，Harness 薄一点）？
   - 交给显式流程（LangGraph：流程复杂，用图锁死）？
   - 交给代码（OpenAI：团队会写 Python 就行）？

2. **你的瓶颈在哪？**
   - 开发速度 → 代码派（OpenAI）；
   - 运行稳定性 → 显式派（LangGraph）；
   - 团队角色结构 → 角色派（CrewAI）；
   - 与特定模型深度耦合 → 薄派（Anthropic）。

3. **未来演进？**
   - 模型会越来越强 → 选「模型越强越受益」的架构（薄派趋势）；
   - 流程会越来越复杂 → 选「可显式建模」的架构。

## 小结

- **同**：五大框架都实现了十二大核心模块的某个子集，模式高度趋同；
- **异**：设计哲学决定了各自的复杂度模型、调试方式、心智负担；
- **选型**：没有绝对优劣，只有场景适配——先看你的瓶颈，再选复杂度分配方式。
