# 框架 2：OpenAI Agents SDK

## 一句话定位

**代码优先设计理念的代表**——开发者用原生 Python 写工作流，Harness 由 `Runner` 类承载，主打开发者友好、快速落地。

## 设计哲学

- **代码优先**：一切皆代码，工作流用原生 Python 编写，**无需学习专用图 DSL**；
- **开发者友好**：降低心智负担，让 Python 开发者开箱即用；
- **快速落地**：从零到生产级应用的速度是核心卖点。

## 核心机制

### 1. Runner 类：Harness 的载体

- 通过 `Runner` 类实现 Harness——它就是「编排循环 + 上下文 + 工具调度」的执行载体；
- 支持三种运行模式：

| 模式 | 特点 |
| --- | --- |
| **异步（async）** | 高并发场景，事件驱动 |
| **同步（sync）** | 简单场景，线性执行 |
| **流式（stream）** | 流式输出，边生成边消费 |

### 2. 工作流：原生 Python

- 智能体、任务、工具、循环都用标准 Python 定义与组合；
- 对比：LangGraph 需要学习图 DSL（节点/边/条件），OpenAI 保持「就是写代码」的直觉；
- 收益：团队已有 Python 技能即可迁移，调试用标准工具链。

### 3. 状态管理：四种策略

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| 应用内存 | 状态在进程内 | 单机轻量 |
| SDK 会话 | 框架管理会话 | 标准路径 |
| 服务器端对话 API | 服务端托管 | 分布式 |
| previous_response_id 链式调用 | 轻量引用上一条响应 | 极简场景 |

### 4. 多智能体：两种模式

| 模式 | 机制 | 关键区别 |
| --- | --- | --- |
| **Agents-as-tools** | 专家 Agent 作为工具被调用，处理细分任务 | 调用后拿结果回来，主 Agent 保持控制 |
| **Handoffs（交接）** | 任务全面交接给另一个 Agent | 控制权转移，换角色继续 |

## 优点

- **上手快**：Python 开发者零门槛；
- **托管工具齐全**：官方提供联网搜索、代码解释器、文件检索等托管工具，开箱即用；
- **部署灵活**：四种状态策略覆盖从单体到分布式的部署形态；
- **生态友好**：与 OpenAI 平台能力（模型、工具、MCP）深度打通。

## 局限与思考

- **显式流程控制弱于图框架**：复杂多分支、严格状态机场景，代码化的流程表达不如 LangGraph 的图结构直观；
- **平台耦合**：托管工具与状态策略部分依赖 OpenAI 平台，迁移到其他模型生态需改造；
- **适用判断**：当「团队熟 Python + 要快速交付生产应用 + 流程复杂度可控」时，这是最高性价比的选择。

## 与十二模块的对应关系

| 十二模块 | OpenAI Agents SDK 的落地 |
| --- | --- |
| 编排循环 | Runner 类驱动，同步/异步/流式 |
| 工具 | 函数调用 + 官方托管工具 + MCP 服务器工具 |
| 状态检查点 | 四种互斥状态策略适配部署场景 |
| 结构化输出 | Pydantic Schema 约束 |
| 护栏 | 输入/输出/工具三层护栏 + 绊线机制 |
| 子 Agent | Agents-as-tools + Handoffs |

## 小结

| 维度 | 要点 |
| --- | --- |
| 哲学 | 代码优先：原生 Python，无需图 DSL |
| 核心 | Runner 类承载 Harness |
| 运行模式 | 异步 / 同步 / 流式 |
| 状态 | 四种策略适配不同部署 |
| 多智能体 | Agents-as-tools（拿结果）/ Handoffs（交控制权） |
| 适合 | 快速落地生产级应用、Python 团队、流程可控场景 |
