# 框架 4：CrewAI

## 一句话定位

**基于角色的多智能体架构代表**——把智能体、任务、团队解耦，像组建一个团队一样组建 AI 协作系统。

## 设计哲学

- **角色分工**：每个智能体是一个「角色」，有明确的职责、技能、背景设定；
- **团队协作**：多个角色组成「团队」（Crew），像真实团队一样协作完成任务；
- **声明式配置**：角色、任务、协作关系用声明式方式定义，贴近业务语言。

## 核心概念

| 概念 | 含义 | 类比 |
| --- | --- | --- |
| **Agent（智能体）** | 一个有角色设定、目标、工具和记忆的独立个体 | 团队里的成员 |
| **Task（任务）** | 分配给智能体的具体工作（含描述、期望输出、上下文） | 工单/任务书 |
| **Crew（团队）** | 组织智能体与任务的协作单位 | 项目组 |
| **Flows 层** | 用于路由与验证的流程控制层 | 项目经理/流程引擎 |

### 智能体、任务、团队如何解耦？

- **Agent 定义「谁来做」**：角色、技能、工具、记忆；
- **Task 定义「做什么」**：目标、输入、输出要求；
- **Crew 定义「怎么组织」**：哪些 Agent、哪些任务、怎么协作；
- 三者独立定义、自由组合——同一批 Agent 可以接不同任务，同一任务可以配不同团队。

## Flows 层：路由与验证

- **Flows** 是 CrewAI 的流程编排层，负责：
  - **路由**：任务按条件流转给合适的 Agent；
  - **验证**：在任务交接点检查输出质量；
  - **状态**：管理任务执行顺序与依赖。

> 可以理解为：Agent/Task/Crew 是「业务组件」，Flows 是「业务流程引擎」——把组件串成可执行、可验证的流程。

## 优点

- **贴近业务**：角色化声明让业务人员也能理解系统结构；
- **协作自然**：多角色分工符合真实团队运作方式，适合业务天然按角色划分的场景；
- **模块化**：Agent、Task、Crew 解耦，复用与重配灵活。

## 局限与思考

- **精细控制弱于图框架**：复杂条件分支、严格状态机的表达不如 LangGraph 精确；
- **角色粒度设计是难点**：角色分得太粗，协作不起来；分得太细，调度开销大；
- **适用判断**：当业务结构天然是「多角色团队协作」（如：调研员→分析师→撰稿人→审核人）时，CrewAI 的抽象与业务同构，开发效率最高。

## 典型应用场景

- 内容生产流水线：选题 → 调研 → 撰写 → 校对 → 发布，每个环节一个角色；
- 业务流程自动化：客服接待 → 技术诊断 → 升级处理 → 反馈归档；
- 多领域专家协作：法律 + 财务 + 技术多角色联合评估。

## 与十二模块的对应关系

| 十二模块 | CrewAI 的落地 |
| --- | --- |
| 编排循环 | Flows 层驱动任务流转 |
| 工具 | 每个 Agent 可配置自己的工具集 |
| 记忆 | Agent 级记忆 + 任务上下文 |
| 子 Agent | 多角色多 Agent 并行协作 |
| 验证 | Flows 中的验证环节 |

## 小结

| 维度 | 要点 |
| --- | --- |
| 哲学 | 角色分工 + 团队协作，声明式配置 |
| 核心抽象 | Agent（谁做）/ Task（做什么）/ Crew（怎么组织）/ Flows（怎么流转） |
| 特点 | 贴近业务、模块化、协作自然 |
| 适合 | 团队式、多角色的复杂任务场景 |
| 注意 | 角色粒度设计是核心难点 |
