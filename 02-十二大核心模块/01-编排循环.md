# 模块 1：编排循环（Orchestration Loop）

## 一句话定位

**编排循环是整个智能体的心跳，是所有行为的核心引擎。** 无论是简单的问答，还是复杂的代码重构、数据分析，所有智能体的行为都始于编排循环，也终于编排循环。

## 它的运行逻辑

编排循环的逻辑非常清晰，是一个标准的四步流程：

```
┌─────────────────────────────────────────────┐
│                编排循环（Loop）                │
│                                             │
│  ① 组装完整提示词                              │
│     （系统指令 + 工具信息 + 记忆内容 + 对话历史） │
│             │                               │
│             ▼                               │
│  ② 发送给大模型，等待输出                      │
│             │                               │
│             ▼                               │
│  ③ 解析模型输出，判断是否需要调用工具           │
│     ├─ 需要工具 → ④执行工具调用                │
│     └─ 不需要  → 输出最终答案，终止循环         │
│             │                               │
│             ▼                               │
│  ④ 将工具执行结果返回给模型                    │
│             │                               │
│             └─────→ 回到 ①，重复流程           │
└─────────────────────────────────────────────┘
```

循环会一直重复，直到**任务完成**或**触发终止条件**（详见模块 12：初始化与环境搭建中的终止条件清单）。

## 具体实现：ReAct 循环与 TAO 循环

我们常说的两类循环，本质都是编排循环的具体实现：

- **ReAct 循环**（Reason + Act）：模型交替输出「推理（Reason）」与「行动（Act）」，观察工具结果后继续推理，形成「思考→行动→观察」的迭代；
- **思考-行动-观察（TAO）循环**：Think-Act-Observe，与 ReAct 同源同构，只是命名与流程组织方式不同。

## 关键洞察：复杂度藏在循环管理的细节里，而非循环本身

从代码结构来看，编排循环往往只是一个简单的 `while` 循环：

```python
while not task_done:
    prompt = assemble_prompt(state)      # ① 组装
    output = llm(prompt)                 # ② 推理
    if not output.has_tool_calls():
        break                            # ③ 无工具调用 → 结束
    result = execute_tool(output.tool_calls)  # ④ 执行
    state = update_state(state, result)
```

看似毫无技术含量，但**真正的复杂度全藏在循环管理的细节里**：

- 上下文用完了怎么办？（压缩、屏蔽）
- 工具调用超时/失败怎么办？（错误处理）
- 循环会不会无限转下去？（最大轮次、Token 预算、终止条件）
- 每轮之间的状态怎么传递？（记忆、检查点）
- 工具结果太大怎么回填？（观察屏蔽）

也就是说：**循环本身是「笨」的，聪明在包围它的那十一个模块里。**

## Anthropic 的定位：笨循环（Dumb Loop）

Anthropic 对自家编排循环的定位很有意思——他们称之为 **「笨循环」（dumb loop）**：

- **所有智能决策、逻辑思考都由模型完成**（模型负责「想」）；
- **Harness 的运行时只负责按流程转场、调度任务，不参与核心推理**（Harness 负责「跑」）。

### 为什么这样设计？

1. **分工明确**：模型专注智能输出，Harness 专注稳定执行，各司其职；
2. **大幅降低系统复杂度**：运行时逻辑保持简单，出问题的面更小，调试更容易；
3. **可演进**：模型变强时，「笨循环」无需改造即可承接更强的推理能力（呼应「脚手架」隐喻：模型越强，Harness 越应该薄）。

## 为什么所有行为都始于、终于编排循环？

- **始于**：用户的任何请求，第一步都是被编排循环组装成提示词送进模型；
- **终于**：直到模型输出不再需要工具调用（或触发终止条件），循环结束，结果交付；
- 中间无论嵌套多少子智能体、多少工具调用，最外层的驱动引擎永远是编排循环。

## 常见问题与思考

### Q1：为什么不能用「一次性大提示词」替代循环？

一次性把任务全抛给模型，模型无法观察中间结果、无法基于反馈修正。编排循环的价值在于**逐轮观察-修正**，这是复杂任务成功的必要条件。

### Q2：编排循环里要不要加入业务规则？

不建议。把决策留给模型，把流程留给循环。业务规则应该放到护栏（Guardrails）与验证（Verification）模块，而不是塞进循环体，否则「笨循环」会变「复杂循环」，失去简单性红利。

### Q3：怎么判断循环「转得够不够」？

不是轮数越多越好。终止条件要明确：任务完成、无工具调用、达到最大轮次、Token 预算耗尽、护栏触发、用户中断、安全拒绝——这些都是合法出口（详见模块 12）。

| 维度 | 要点 |

| 角色 | 心跳 / 动力核心 |
| 实现 | ReAct、TAO 循环 |

| 复杂度来源 | 不在循环本身，在循环管理的细节 |
