# 模块 5：提示词组装（Prompt Assembly）

## 一句话定位

**提示词组装定义了模型在每一轮推理中看到的世界**——它是连接上下文、记忆、工具、用户需求的最后一环。

## 它不是简单的拼接

提示词组装**不是简单的拼接**，而是**分层堆叠的结构化过程**：优先级明确、逻辑清晰。每一层都有各自的职责，组装顺序决定了模型「先看到什么、后看到什么、以什么为最高准则」。

## 标准的组装顺序

综合行业实践，典型的组装顺序如下：

```
① 系统提示词      → 定义智能体的身份和核心规则
② 工具定义        → 告知可用的能力（工具 Schema）
③ 记忆文件        → 总结历史经验（长期记忆）
④ 对话历史        → 获取当前任务进度（短期记忆）
⑤ 当前用户消息    → 得到最新需求
```

| 顺序 | 内容 | 作用 |
| --- | --- | --- |
| ① 系统提示词 | 身份、角色、核心规则 | 最高层约束，定义「我是谁、我遵循什么」 |
| ② 工具定义 | 可用工具 Schema | 让模型知道「我有什么能力」 |
| ③ 记忆文件 | 长期记忆摘要 | 让模型知道「我以前知道什么、做过什么」 |
| ④ 对话历史 | 本会话过往交互 | 让模型知道「现在进行到哪一步」 |
| ⑤ 当前消息 | 用户最新输入 | 让模型知道「现在要做什么」 |

## 案例：OpenAI Codex 的优先级栈

OpenAI 的 Codex 采用了严格的**优先级栈**设计，从高到低：

| 优先级 | 内容 |
| --- | --- |
| 最高 | 服务器控制的系统消息 |
| ↓ | 工具定义 |
| ↓ | 开发者指令 |
| ↓ | 用户指令 |
| 最低 | 对话历史 |

### 为什么优先级如此严格？

- **核心规则不能被覆盖**：如果对话历史或用户消息能改写系统提示词，智能体的行为就不可控了；
- **越靠近「控制面」的信息越优先**：服务器控制的消息是系统底线，绝不能被子级内容污染；
- **对话历史放最后**：历史是「参考材料」，不是「行为准则」。

> 这种「控制面与数据面分离」的设计，确保核心规则不被冗余信息覆盖，保证智能体行为不偏离预期。

## 组装质量直接影响输出准确率

提示词组装不是「顺序对了就行」，每个环节都可能引入问题：

| 常见问题 | 后果 | 对策 |
| --- | --- | --- |
| 系统提示词被历史消息稀释 | 模型忘记核心规则 | 优先级栈 + 位置前移 |
| 工具定义太多太长 | 挤占有效上下文 | 按需注入最小工具集 |
| 记忆文件与当前事实冲突 | 模型被旧记忆带偏 | 「记忆是提示不是事实」+ 现场核对 |
| 历史消息顺序混乱 | 模型误解任务进度 | 严格按时间顺序、必要时压缩 |

## 设计原则与思考

### 1. 分层而非平铺

- 平铺拼接会让所有信息等权，模型无法区分「规则」与「参考」；
- 分层 + 明确优先级，模型才知道什么不能违背。

### 2. 每一轮都要重新组装

- 每轮推理的上下文都在变化（新增了工具结果、更新了记忆）；
- 组装必须发生在每一轮循环内（对应模块 1 编排循环的第一步）。

### 3. 与上下文管理协同

- 组装决定「放什么进去」，上下文管理决定「怎么控制总量」；
- 组装层负责结构与优先级，上下文层负责压缩与屏蔽，两者配合完成「最小高信噪比 Token 集合」。

### 4. 可观测性

- 生产环境应记录「每一轮实际组装出的提示词结构」（各层长度、是否触发压缩），
- 排查「模型为何跑偏」时，先看组装快照，比盲猜模型行为高效得多。

## 小结

| 维度 | 要点 |
| --- | --- |
| 角色 | 模型每轮推理「看到的世界」的定义者 |
| 核心 | 分层堆叠 + 明确优先级 |
| 标准顺序 | 系统提示词→工具→记忆→对话历史→当前消息 |
| 标杆 | OpenAI Codex 优先级栈（控制面 > 数据面） |
| 原则 | 核心规则不可被覆盖；每轮重装；与上下文管理协同 |
