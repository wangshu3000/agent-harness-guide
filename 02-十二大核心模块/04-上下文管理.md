# 模块 4：上下文管理（Context Management）

## 一句话定位

**上下文管理是生产级智能体最容易默默翻车的重灾区，也是所有 AI 工程师必须攻克的难题。** 它的核心敌人只有一个：**上下文腐烂（Context Rot）**。

## 问题根源：上下文腐烂（Context Rot）

### 什么是上下文腐烂？

随着对话推进，塞进上下文的信息越来越多——历史消息、工具输出、检索结果、中间草稿……当内容不断膨胀，模型的**指令遵循能力**和**推理准确率**会持续下降。这就是上下文腐烂。

### 硬核证据：Lost in the Middle 研究

- **斯坦福大学《Lost in the Middle》研究**与 **Chroma 团队的实验**相互印证：
- 当关键信息落在**上下文窗口的中间位置**时，模型性能会**暴跌 30% 以上**；
- 模型对开头（primacy，首因效应）和结尾（recency，近因效应）的内容记得更牢，中间区域成了「注意力黑洞」。

### 为什么百万 Token 也救不了？

即便如今主流模型已经支持百万级 Token 上下文：

- 上下文越长，模型的注意力越分散，关键信息被稀释；
- 长上下文的推理延迟与成本线性增长；
- 信息一多，模型更容易「被无关内容带偏」，指令遵循能力下降。

> 结论：**上下文窗口大 ≠ 可以随便塞。** 稀缺的不是容量，是「有效信息密度」。

## 生产环境四大应对策略

### 策略 1：压缩（Compaction）

- **做什么**：当上下文接近上限时，对对话历史做摘要处理；
- **保留**：核心决策、未解决的问题；
- **丢弃**：冗余的工具输出、过时的中间过程；
- **代价**：压缩会丢失细节，需权衡「保留推理痕迹」与「节省 token」。

### 策略 2：观察屏蔽（Observation Masking）

- **做什么**：隐藏旧工具输出的细节，但**保留工具调用记录**；
- **收益**：既减少 token 消耗，又不丢失「模型调过什么工具、按什么顺序调」的关键逻辑链；
- **适用**：工具结果很长但已消化完毕的场景。

### 策略 3：即时检索（Just-in-time Retrieval）

- **做什么**：维护轻量级索引，**动态加载**所需数据，而不是加载完整文件；
- **范例**：Claude Code 用 `grep`、`glob`、`head`、`tail` 命令精准提取内容片段，而不是把整个文件读进上下文；
- **收益**：按需取用，把大文件挡在上下文之外。

### 策略 4：子智能体委派（Sub-agent Delegation）

- **做什么**：将复杂任务拆给子智能体去探索、执行；
- **关键**：最终只返回 **1000–2000 Token 的精简摘要**回主智能体；
- **收益**：子智能体在独立上下文里干活，主智能体的上下文压力大幅降低（详见模块 11）。

## 终极目标：最小的高信噪比 Token 集合

Anthropic 的上下文工程指南明确给出了这一模块的终极目标：

> **找到最小的高信噪比（high signal-to-noise）Token 集合**——用最少的关键信息，最大化实现预期任务效果。

### 拆解这个目标

- **信噪比**：有用信息（信号）与无用信息（噪音）的比例；
- **最小**：能少就少，绝不为了「保险」把无关内容塞进去；
- **最大化效果**：压缩不是目的，任务成功率才是目的——压缩过头导致信息缺失同样失败。

> 上下文管理的本质是**信息经济学**：每塞进一个 token，都要回答「它对任务成功有什么贡献？」

## 四种策略怎么选？

| 场景 | 推荐策略 |
| --- | --- |
| 长对话接近窗口上限 | 压缩 + 观察屏蔽 |
| 需要引用大型文件/知识库 | 即时检索 |
| 任务复杂、信息海量 | 子智能体委派 |
| 生产系统 | 四者组合使用，形成分级防线 |

## 常见问题与思考

### Q1：压缩会丢关键信息怎么办？

设计压缩器时要有「优先级规则」：决策结论 > 中间推理 > 工具输出细节；未解决问题必须保留。压缩后再出问题，靠「观察屏蔽 + 即时检索」补查原文。

### Q2：上下文管理是运行时问题还是设计问题？

两者都是。运行时靠上述策略兜底；设计上靠「最小必要信息」原则——从一开始就别把不必要的东西放进上下文，比事后清理更高效。

### Q3：怎么衡量上下文管理做得好不好？

可观测指标：每轮平均 token 数、任务成功率、模型引用早期信息的准确率、上下文超限触发的次数。管理得当的系统，token 消耗平稳、任务成功率高。
