# 模块 7：状态与检查点（State & Checkpointing）

## 一句话定位

**状态与检查点是智能体实现断点续跑、可回溯和可调试的核心**，解决了长周期任务中断后无法恢复的痛点。

## 痛点：长任务中断，一切归零

长流程任务——大型项目代码重构、多步骤数据分析、跨天执行的业务流水线——可能持续**几个小时甚至几天**：

- 中途崩溃、进程被杀、服务重启、网络断开……
- 若没有状态保存，**所有进度都会归零**，只能从头再来；
- 更糟的是，重跑还可能产生副作用（重复写文件、重复发请求）。

## 状态到底是什么？

状态（State）是智能体在任意时刻的「可序列化快照」，通常包括：

| 状态内容 | 说明 |
| --- | --- |
| 任务目标与计划 | 当前在执行什么、还剩什么 |
| 对话历史/上下文 | 已经交换过的信息 |
| 工具调用记录 | 调过哪些工具、结果如何 |
| 中间产物 | 生成的文件、数据、草稿 |
| 决策记录 | 为什么做某个选择（可回溯的关键） |

## 三大框架的状态管理方案对比

### 1. LangGraph：类型化字典 + 归约器 + 超级步骤

- **状态建模**：类型化字典（TypedDict），显式声明每个字段的类型；
- **状态更新**：通过**归约器（Reducer）**合并状态更新——不是直接覆盖，而是按规则合并（如「累加」或「保留最新」）；
- **检查点**：在**超级步骤（superstep）边界**触发，即每完成一个「节点执行 + 边转移」的完整步骤后保存；
- **恢复**：支持中断后无缝恢复；
- **亮点**：甚至能实现**时光倒流式调试**——回退到任意检查点，重放不同路径。

### 2. OpenAI：四种互斥的状态策略

| 策略 | 说明 | 适用场景 |
| --- | --- | --- |
| 应用内存 | 状态存在进程内存 | 单进程、轻量 |
| SDK 会话 | 由 Agents SDK 管理会话对象 | 标准开发路径 |
| 服务器端对话 API | 状态由服务端托管 | 分布式、多实例 |
| `previous_response_id` 链式调用 | 轻量级引用上一条响应 | 极简场景，无需持久化 |

> 四种策略互斥选择，适配不同部署场景——从单机 Demo 到分布式生产。

### 3. Claude Code：Git 提交即检查点

Claude Code 的设计极具特色，直接借用版本控制能力：

- **Git 提交作为检查点**：任务每到一个里程碑，自动提交；崩溃后 `git` 恢复即可续跑；
- **进度文件作为结构化草稿本**：把「任务进度、待办、决策」写进可读的进度文件；
- **收益**：检查点天然可版本化、可 diff、可回溯、可审计，且对人类可读。

## 设计原则与思考

### 1. 检查点频率是权衡

- 太频繁：I/O 开销大、性能下降；
- 太稀疏：崩溃丢失的进度多；
- 原则：在**状态变更边界**（每个完整步骤后）落点，兼得安全与性能（LangGraph 的 superstep 边界即此思路）。

### 2. 状态要「可序列化、可恢复」

- 内存对象（如打开的连接、文件句柄）不能直接进检查点；
- 设计时就要把状态建模成「可序列化数据」，否则无法断点续跑。

### 3. 可回溯性是调试的生命线

- 「时光倒流」式调试的价值：复现问题、重放决策、找出哪一步跑偏；
- 没有检查点，长任务的故障几乎无法定位。

### 4. 与记忆的分工

- 记忆（模块 3）负责「记住什么信息」；
- 检查点负责「恢复到什么进度」；
- 记忆关注内容，状态关注执行轨迹。

## 常见问题

### Q：检查点里存了敏感信息怎么办？

检查点可能包含用户数据、密钥、对话内容。生产环境必须：加密存储、访问控制、按数据保留策略清理，并纳入合规审计。

### Q：恢复到检查点后，工具副作用怎么处理？

这是最难的问题之一——检查点恢复了「状态」，但无法回滚已发生的真实副作用（已发出的邮件、已提交的代码）。对策：
- 工具执行前做好幂等设计（同一操作可重复执行结果一致）；
- 高风险副作用工具设计为「需确认才执行」，避免恢复后自动重放破坏性操作。
