# 模块 9：护栏（Guardrails）

## 一句话定位

**护栏是智能体的安全红线**——防止智能体做出越权、有害、违规操作，是企业级应用的核心保障。

## 为什么需要护栏？

智能体的危险在于它「会行动」：能写文件、删数据、发消息、调用外部服务、访问敏感资源。一旦行为失控：

- **越权**：调用了不该调的高风险操作；
- **有害**：生成了违规、有害、误导性内容；
- **违规**：触犯合规红线（数据泄露、未授权访问）。

护栏就是在这条路上设下的**红线与急停装置**。

## OpenAI 的三层防护体系

OpenAI 的 SDK 实现了三层防护，覆盖智能体的完整生命周期：

| 层级 | 运行时机 | 职责 |
| --- | --- | --- |
| **输入护栏** | 智能体接收用户请求时 | 过滤恶意和违规输入（注入攻击、恶意指令） |
| **输出护栏** | 最终输出前 | 确保输出内容合规安全 |
| **工具护栏** | 每次调用工具时 | 管控工具调用权限，防止高风险操作 |

### 绊线机制：紧急制动

- 一旦触发护栏的绊线（tripwire），智能体**立即终止当前操作**；
- 这是「急刹车」设计：宁可中断任务，也不让危险操作继续。

> 理解三层的关系：输入护栏守「入口」，输出护栏守「出口」，工具护栏守「每一个动作」。安全不是一次检查，而是全程检查。

## Anthropic 的护栏设计：权限与推理解耦

Anthropic 的设计更加彻底，在**架构上**解决问题：

> 将**权限执行**与**模型推理**完全解耦：模型只负责「想做什么」，工具系统负责「能做什么」，两者互不干扰。

### 为什么解耦？

- 模型是「自由思考者」，不该同时是「执法者」——让它自己判断权限，等于让它自己当自己的警察；
- 权限判断是确定性逻辑（规则、清单、配置），交给确定性的工具系统执行，更可靠、可审计；
- 解耦后，即使模型「想」做危险操作，也「做」不了——权力被架构隔离。

### Claude Code 的实践细节

- **独立管控约 40 种离散的工具能力**（读文件、写文件、执行命令、访问网络……逐项独立授权）；
- **三个阶段严格把关**：

| 阶段 | 把关内容 |
| --- | --- |
| 项目加载时 | 建立信任体系（项目信任级别、初始授权范围） |
| 每次调用工具前 | 检查权限（该操作是否被当前授权覆盖） |
| 高风险操作 | 必须获得用户的明确确认（人在环上） |

> 从根源上杜绝安全风险：不是「事后发现」危险操作，而是「事前就不让发生」。

## 设计原则与思考

### 1. 安全 ≠ 一味禁止

- 护栏要「精确」：该放行的流畅放行，该拦截的坚决拦截；
- 一刀切全禁，智能体就废了；全放行，生产就完了。

### 2. 权限要「最小化、可配置」

- 默认最小权限，按任务需要临时放开；
- 权限配置应可审计、可回滚。

### 3. 人在环上（Human-in-the-loop）

- 高风险操作（删除、支付、外发、写生产数据）要用户确认；
- 确认机制是「最后的防线」，也是责任边界。

### 4. 护栏触发要可观测

- 触发记录（哪个护栏、哪个操作、哪个模型输出）要完整留存；
- 安全事件必须可复盘，才能持续加固。

### 5. 与错误处理（模块 8）区分

- 护栏是「阻止不该发生的」；
- 错误处理是「处理已经发生的失败」；
- 前者是预防，后者是修复，不要混为一谈。

## 常见问题

### Q：护栏会不会影响模型性能？

会有一点，但这是必要成本。好的护栏设计（解耦、分层）能把性能损耗降到最低——权限检查是微秒级的确定性逻辑，相比模型推理的延迟可以忽略。

### Q：用户明确要求危险操作怎么办？

护栏是红线不是建议。即使模型「想」执行，工具系统也应拒绝或要求更高等级授权。安全规则不因用户指令而撤销（合规边界由组织策略决定）。

## 小结

| 维度 | 要点 |
| --- | --- |
| 角色 | 安全红线 / 企业级保障 |
| OpenAI 三层 | 输入护栏 + 输出护栏 + 工具护栏，绊线急停 |
| Anthropic | 权限执行与模型推理完全解耦，约 40 种能力独立管控，三阶段把关 |
| 关键设计 | 事前预防、最小权限、人在环上、触发可观测 |
| 核心原则 | 让模型想做的做不了，让该做的畅通无阻 |
